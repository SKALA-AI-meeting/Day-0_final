# FLOW — Day Zero: AI 동료와의 음성 토론으로 태도를 미리 본다 (15분)

근거 자료: main 브랜치의 `PRD.md`(장 번호로 표기)와 `docs/`.
그림·화면: `assets/`(덱 크기로 새로 그린 diagram-*.svg, 데모 세션 녹화 영상, e2e·실제 LLM 리포트 캡처, 상황 일러스트). 자산 목록은 ASSETS.md.

## 발표 목적
서비스를 함께 만들 사람과 이 서비스가 필요한 기업이 15분 안에 "어떤 문제를, 무엇으로, 왜 믿을 수 있게 풀고, 누구에게 어떤 성과를 주는지"를 이해하고, 그다음 "실제로 어떻게 만들었고 돌아가는지"를 확인하게 한다.

## 확정한 선택
- 순서: 문제 → 솔루션 → 근거 → 이해관계자 → 비즈니스 성과 → 아키텍처(개발 설계) → 기능 → 시연 → 마무리
- 설계 묶음(아키텍처·에이전트·MCP·하네스)은 개발 설계 내용으로 4장 모두 남긴다. 대본은 "같은 조건 증명·측정 오염 방지·감사 대응·원가 통제" 같은 비즈니스 의미를 함께 말한다
- 화면: 브라우저 라이브 + PDF. 영상이 있는 장은 PDF에 같은 장면의 정지 화면
- 상태 배지는 "구현됨"(기능이 돌아간다)과 "제안 · 파일럿 전 가설"(효과는 아직 검증 전)로 나눈다
- 장 제목은 명사형으로 끝낸다

## 핵심 메시지
> 인성검사는 꾸밀 수 있고 토론 면접은 비싸다. Day Zero는 면접 전에 AI 동료 3명과 음성으로 토론하게 해, 담당자가 실제 행동 근거로 판단하게 돕는다. 기존 면접·검사를 대체하지 않고 보완한다.

## 전제
- 청중: 서비스를 함께 만들 사람(기획·개발)과 이 서비스가 필요한 기업(인사담당자·도입 결정권자). 지원자는 청중이 아니다.
- 발표 시간: 15분(900초), 발표자 1명.
- 요청: 마지막 장에서 파일럿에 함께할 기업을 찾는다.
- 함께 가는 산출물: PRD(시장 규모·경쟁 세부·리스크 표)는 질의응답 대비로 둔다.
- 렌더 타깃: 브라우저 라이브 + PDF.
- AI 고도화(테스트 피드백 반영) 이야기는 넣지 않는다.

## 구현 상태 표기
- `구현됨`: 1·3·7~14장. MVP에 구현됐고 e2e·데모 화면 기록이 있다. 리포트 정확도는 구현과 별개로 파일럿 전 가설이다.
- `외부 조사·연구`: 2·4장 수치.
- `제안`: 5·6장 이해관계자 이득·성과·가격. 파일럿을 하지 않았으므로 "검증할 가설"로 말한다.
- `예정`: 15장 파일럿.

## 흐름 자가 점검
- 시간 역행: 없음. 문제(2) → 해결된 모습(3) → 믿을 근거(4) → 누가(5) → 얼마나(6) → 어떻게 만들었나(7~10) → 무엇을 쓰나(11~13) → 보여 주기(14) → 다음(15).
- 결과 지연: 3장(약 1분 30초)에서 실제 음성 회의 영상이 먼저 나온다. 기능 화면은 9분쯤, 시연은 12분쯤이다. 사용자가 고른 순서다.
- 중복 주장: 3장(무엇)과 11장(순서)이 겹칠 수 있다. 3장은 한 줄 해결책, 11장은 단계 흐름으로 나눈다. 14장 시연은 12·13장을 다시 설명하지 않고 보여 주기만 한다. 4장 비교 표는 2장의 "꾸며진다·비싸다" 두 축을 그대로 잇는다.
- 질문 수: 장마다 하나.
- 밀도 편차: 4장(비교 표)과 7장(아키텍처)이 가장 무겁다. 1·3·15장은 가볍게 둔다.
- 결론 연결: 15장은 6장의 "파일럿에서 두 지표부터"와 이어진다.
- 분담 위반: 도구 목록·하네스 수치·시장 규모는 덱에서 뺐다.
- 정직성: 5·6장은 `제안`, 13장은 "정확도는 가설", 3장의 "싸게"는 원가 추정으로만 말한다. 데모는 15분 세션이라고 밝힌다.
- 금지 표현: 합격·불합격·순위·점수·총점, "주담당"·"리드"를 쓰지 않는다. "수준·근거·확신도·담당자가 최종 평가"로 쓴다. 5·6장에서 "면접 대상을 AI가 거른다"로 읽히지 않게 "담당자가 리포트를 참고해 정한다"로 쓴다.
