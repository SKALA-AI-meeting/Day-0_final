# 설계 결정 기록

## 2026-10-22 턴 기반 음성 토론 전환 설계

사용자가 구현을 승인한 음성 토론 구조다. 현재 구현 범위는 [음성 구현 문서](architecture/voice.md)를 따른다. 상세 청사진과 미확정 항목은 [음성 턴 설계](architecture/voice-turns.md). 구현 PR에서 PRD와 계약을 함께 반영한다.

| 구분 | 결정·제안 | 이유 | 대안 |
|---|---|---|---|
| 요청 확정 V1 | 지원자 1명·AI 동료 3명의 턴 기반 음성 토론. 검증된 AI 텍스트를 TTS로 순차 재생하고 최종 STT 텍스트를 기존 `message.send` 경로로 제출 | 기존 의도 분류·그래프·페르소나·MCP·합의·평가와 내부 메시지 근거 보존 | 실시간 양방향 오디오: 이번 범위 밖 |
| 요청 확정 V2 | 별도 Voice Turn Controller가 6개 상태와 실행 완료·재생 완료를 구분. 입력창·말풍선 제거, 완료 버튼과 시간 종료로 녹음 제출 | 생성 종료만 보고 마이크를 여는 경쟁 방지 | 브라우저 타이머만 사용: 재연결·중복 제출 방어 불충분 |
| 설계 제안 V3 | API 내부 모듈 + 브라우저 미디어 어댑터, DB 턴·재생·발언 시도 기록. 기본 발언 한도 60초를 채용 건에 고정 | 배포 단위 증가 없이 복구·동일 조건 확보 | 음성 전용 마이크로서비스: MVP 운영 부담 |
| 설계 제안 V4 | 단계·세션 마감은 기존 절대 시각 유지. 발언권 부여 뒤 녹음 시작부터 최대 60초, 단계 잔여시간으로 절단. 마감 뒤 도착한 STT는 과거 단계의 참고 기록으로만 보존 | 마감 연장과 새 단계 오귀속 방지. 이 정책의 제약은 상세 설계 6장에 명시 | 모든 음성 대기 동안 시계 정지: 카드·세션 시간 체계 변경 |
| 설계 제안 V5 | 게시 기록과 실제 재생 확인을 분리하고 카드 장면의 평가 입력은 청취 가능했던 범위로 제한 | 들리지 않은 장면을 지원자 행동의 전제로 삼지 않음 | 게시를 청취로 간주: 기존 텍스트 전달 기준으로는 음성 장애를 설명할 수 없음 |
| 설계 권장 V6 | 초기 음성 시연은 Azure Speech F0의 일반 Neural TTS + 표준 ko-KR STT, 동시에 진행하는 음성 세션 1개. 일상 개발은 FakeSpeech. Google TTS와 로컬 MeloTTS+OpenVoice V2 / faster-whisper는 교체 후보 | 무료량·서로 다른 한국어 voice 3개·운영 준비 부담을 함께 고려. 한국어 품질·지연 우열은 아직 미측정 | Google은 더 큰 TTS 무료량이 있지만 초과 자동 과금, 로컬은 API 요금 없이 장비·배포·품질 검증 부담 |
| 설계 권장 V7 | 음성은 무료 전용 모드 기본, 계정 범위 월 사용량 예약·요청 속도·세션 한도·청구 SKU 확인 후 호출. 유료 전환·공급자 자동 대체 없음. LLM·TTS·STT 별도 원장과 전체 비용 합계 | 무료 호출도 한도를 소모하며 재시도·타임아웃·외부 사용으로 초과할 수 있음. 기존 LLM 상한만으로 음성 비용을 막을 수 없음 | 예산 알림만 사용: 호출 차단이 보장되지 않음 |

V6·V7의 공식 자료 비교·비용 계산·독립 인터페이스·차단 정책은 [음성 서비스·비용 설계](architecture/voice-services.md)에 있다. Azure 어댑터를 구현했다. 클라우드 리소스 생성과 실제 음질·지연 실측은 별도 검증이다.

| 구현 V8 | F0 확인·독립 음성 포트·DB 발언권·완성 WAV 제출·순차 재생을 구현한다. 제어 스냅샷은 별도 REST polling, 전사 제출은 기존 WS를 쓴다. 시작·마감·재연결은 turn_id/generation/epoch로 검증 | 새 음성 WS 이벤트를 늘리지 않고 기존 메시지·seq 경계를 유지 | 모든 제어를 WS 이벤트로 영속 재생 |
| 구현 V9 | 기존 LLM 비용 제한을 유지하고 음성은 무료 SKU·별도 사용량 원장으로 차단한다. 유료 음성/통합 유료 예산 확장은 구현 범위에서 제외 | 초기 시연의 추가 API 비용 차단. 알림만으로 무료량을 지키지 않음 | S0 자동 전환 또는 비용 합계만 관측 |
| 개정 V10 (10-23) | V2의 "말풍선 제거·확인 없이 자동 제출"을 바꾼다. ① 음성 화면 아래에 대화 기록을 둔다. 동료 발언은 재생 위치에 맞춰 기록 말풍선에 한 문장씩 더한다(목소리보다 글이 앞서지 않게). ② 내 차례에 생각 시간(`VOICE_THINK_SECONDS`, 처음 30초 → 같은 날 팀 회의에서 티키타카를 위해 5초)을 두고 "지금 발언하기"로 일찍 시작한다. ③ 받아 적은 글을 확인 시간(`VOICE_CONFIRM_SECONDS`, 처음 10초 → 팀 회의 뒤 3초) 동안 보여 주고 [이대로 제출]·[다시 녹음 1회]. 두 시간은 채용 건에 고정 | 1차 실사용(10-23): 글이 없어 무엇이 오갔는지 알기 어려움, 글이 목소리보다 먼저 보이면 듣기에 집중하지 못함, 차례가 오자마자 마이크가 켜져 준비할 틈이 없음, 잘못 받아 적힌 글이 그대로 평가 근거가 됨 | 글 수정 후 제출(타자가 들어가 음성 토론 취지가 약해짐), 재생 시작 때 전체 글 표시, 카드 아래 별도 자막 칸(시선이 두 곳으로 나뉨) |
| 개정 V18 (10-23) | 녹음 60초는 첫 발언에서 보장하고 단계 마감은 늘리지 않는다(V4 유지). 강제 차례는 지금 동료 발언이 끝나기를 기다릴 몫 `VOICE_FORCED_WAIT_SECONDS`(30초)를 더해 마감 105초(30 + 생각 5 + 녹음 60 + 여유 10) 전에 온다. 이미 말한 뒤 마감 직전에 다시 말하면 녹음은 마감 10초 전(받아 적기·확인·제출 여유)에서 잘리고, 녹음 전에 "이번 발언은 최대 N초"를 알린다(`speech_limit_seconds`, 10초 안쪽은 녹음 불가). 마감에 걸려 거절된 녹음은 오류로 멈추지 않고 안내만 한다 | 도희: 지원자 녹음 60초 보장. 로컬 동료 발언 115건이 평균 12.5초·90%가 23초 이하·최대 32초라 75초 전 발동이면 동료 발언을 기다리다 잘림. 마감 미루기는 V4·다음 단계 시간을 바꿈. 녹음을 마감 시각에 딱 맞춰 자르면 파일이 마감 뒤에 도착해 늘 거절됐음(10-23 로컬 세션 2건 재현) | 단계 마감을 녹음 시작 때 70초 뒤로 미루기(모든 경우 보장, V4 변경·다음 단계가 짧아짐), 안내 없이 자르기 |
| 개정 V17 (10-23) | 녹음 시작은 지원자가 정한다: 일반 내 차례는 자동 녹음 없이 [발언하기]를 눌러 시작하고, `VOICE_TURN_HOLD_SECONDS`(20초) 동안 차례를 지킨 뒤 지나면 동료가 이어 말한다(손들기로 다시 잡을 수 있음). 손들기·강제 차례는 생각 시간(5초) 뒤 자동 시작([지금 발언하기]로 바로 시작할 수도 있음). 화면은 중범 님 레이아웃의 가운데 칸에 4명 프로필(2x2, 말하는 사람·녹음 중인 지원자 강조)과 차례·녹음·손들기 조작을 두고, 왼쪽 칸은 메모장으로 쓴다(왼쪽 작은 프로필은 인사 화면에서만) | 팀 회의: 발언 타이밍을 지원자가 정하게(적극성), 말하기가 화면의 중심 | 생각 시간 뒤 자동 녹음(V10 ②, 준비 안 된 채 마이크가 켜짐), 메모 가운데·말하기 왼쪽 |
| 개정 V16 (10-23) | 단계 마감 전 강제 차례: 키워드·문제 상황·해결책 단계에서 지원자가 그 단계에 한 번도 말하지 않았고 마감까지 "발언 한도 60초 + 자동 시작 대기(생각 시간) + 여유 10초" 이하가 되면, 단계당 한 번 지원자 차례를 강제한다(동료 발언은 손들기와 같은 규칙으로 넘김). 마감을 늘리지 않고 일찍 발동해 60초 발언이 마감 안에 끝나게 한다. 손들기나 일반 차례로 이미 말했으면 강제하지 않는다. 발언 기록에 `turn_kind: forced`로 남긴다 | 팀 회의: 다음 단계로 넘어가기 전 지원자 의견을 반드시 받기. 기존 침묵 초대(단계 중간 1회)만으로는 단계 끝까지 말할 기회를 놓칠 수 있음. 판단은 코드(결정적), 에이전트 코드는 그대로 | 단계 마감 유예(V4 변경·시계 체계 변경), LLM에 "꼭 물어봐" 지시(보장 안 됨), 동료 최소 발언 수 보장(흐름 문제) |
| 개정 V15 (10-23) | 손들기: 동료가 말하거나 대답을 준비하는 동안 지원자가 손을 들면, 지금 재생 중인 발언은 끝까지 듣고 그 뒤 보호 발언(카드 발언·합의/시간 초과 공지)만 남긴 채 줄 선 동료 발언을 취소하고 바로 지원자 차례를 준다. 지원자 발언보다 먼저 나왔지만 안 들은 동료 발언은 재생하지 않는다. 차례 종류(일반·손들기·강제)와 손든 시점을 발언 기록에 남긴다. 동료 발언 순서·내용(에이전트)은 바꾸지 않는다 | 팀 회의: 끼어들기·티키타카 필요. 끊기는 버튼은 감점이 분명해 안 누르게 되고 완전 자율은 동료 발언을 망침. 손들기는 누구 말도 끊지 않으면서 차례를 앞당김. 카드 장면은 못 들으면 평가가 사라져 보호 | 끼어들기 버튼(즉시 끊기), 말소리 자동 감지(이어폰 필요·오작동), 실시간 양방향 음성(에이전트 구조 우회) |
| 개정 V14 (10-23) | 음성 토론 화면에서 채팅(대화 기록)을 없애고 그 자리에 지원자 메모장을 둔다. 메모는 이 브라우저에만 세션별로 저장하고 서버로 보내지 않으며 평가에 쓰지 않는다. 화면 배치는 중범 님 분할 레이아웃(front/debate-layout-voice)을 쓰고 음성 칸·프로필·메모 칸을 음성 차례 기능에 연결한다 | 팀 회의: 동료 대사를 글로 미리·함께 보여 주면 듣기보다 읽기에 기대게 됨. 음성 토론답게 들으면서 스스로 적게 함. 메모를 평가에 쓰면 평가 기준 변경이라 제외 | 채팅 기록 유지(재생에 맞춰 한 문장씩·끝난 뒤 표시), 메모 서버 저장(DB·계약 변경, 평가 반영 여부 결정 필요) |
| 개정 V13 (10-23) | 말하는 동안 받아 적기: 브라우저가 녹음 중 0.5초마다 PCM16 16kHz 조각을 `/voice/stream`으로 보내고, 서버가 약 10초마다 가장 조용한 0.3초 구간에서 잘라 빠른 받아 적기로 미리 보낸다. 녹음이 끝나면 꼬리만 받아 적어 잇는다. 완성 파일 업로드(V8)는 길이 검사·예비 경로로 유지하고, 조각이 빠지거나 길이가 1초 넘게 다르면 파일 전체로 받아 적는다 | 개선 뒤 실측(60초 발언)에서도 받아 적기 6.2초가 남아 "말 끝 → 동료 목소리 7초 이내" 목표를 막음. 실시간 인식은 측정상 이름 정확도가 낮아(8개 중 4개) 같은 빠른 받아 적기 모델을 조각으로 쓰는 쪽을 택함 | Azure 실시간 인식 스트리밍(이름 정확도 낮음), 완성 파일만 제출(기다림이 소리 길이에 비례) |
| 개정 V12 (10-23) | 동료 발언 재생: 맨 앞 발언의 합성이 끝나면 뒤 발언·에이전트 실행이 남아 있어도 바로 재생한다. 남은 발언이나 실행이 있는 동안 내 차례(USER_READY)를 주지 않는 장벽(V2)은 유지 | 1차 실사용에서 동료 여러 명이 답할 때 첫 목소리까지 최대 13.9초를 기다렸다(전원의 답·합성이 끝날 때까지 대기) | 전원 준비 후 재생(기존) |
| 개정 V11 (10-23) | 받아 적기 기본 경로를 Azure 빠른 받아 적기(fast transcription, REST 한 번)로 바꾸고, 거절되면 기존 SDK continuous recognition으로 같은 파일을 받아 적는다. 채용 건의 동료 이름을 구문 목록으로 함께 보낸다. voice-services.md의 "F0 미지원 유료 Fast로 바꾸지 않는다"를 측정 사실로 고친다 | F0 측정(소리 4~46초, 문장 4개): continuous 0.36~0.46배 → fast 0.05~0.08배, 이름 8개 중 continuous 4개 → fast 8개 정확. 사용분 요금 0원(포털 확인). 요금표가 F0 포함 여부를 밝히지 않아 거절 시 F0 안의 예비 경로를 둔다 | 말하는 동안 소리 조각을 흘려보내는 스트리밍(파일 7~8개 변경), OpenAI 받아쓰기(지금 키 403·유료), 구글·Deepgram·CLOVA(새 계정·키), 로컬 Whisper(도커에서 맥 GPU 불가) |

## 2026-10-20 foundation 리뷰 반영 — **일부 대체됨(2026-10-21 토론형 전환)**: 업무 시뮬레이션 전용 항목(문서·보드·분업·카드 시각·관찰 레이블)은 대체, 일반 규칙은 유지
- 종료 run 실패: `complete()`는 종료 run이 `ok=False`여도 completed로 진행하고 리포트를 발행한다. agent_runs는 failed로 남기고 경고 로그를 찍는다. 이유: 지원자 작업물을 잃지 않기 위해. 대안: 세션 failed(작업물이 리포트로 가지 않음).
- 종료 직렬화: `complete()` 전체(상태 재검증 → 종료 실행 → 재사용 추정 → completed 커밋 → 발행)를 세션 Lock 안에서 하고, Lock 안에서 다시 읽은 상태가 in_progress가 아니면 아무것도 하지 않는다. `run_agent(lock_held=True)`로 같은 Lock의 재획득(교착)을 피한다. 이유: 제출과 만료가 겹쳐도 종료 실행·발행이 한 번만 일어나게. **R5로 대체**: 세션 Lock·`lock_held`는 없다. 종료는 `SessionService.submit` 한 트랜잭션이고 메일박스의 남은 자극은 상태 검사로 skipped([architecture/session-lifecycle.md](architecture/session-lifecycle.md) "세션 메일박스").
- web mocks 소유권 분리: `mocks/index.ts`(foundation)는 `mocks/admin.ts`(web-admin)·`mocks/office.ts`(web-office)의 ROUTES를 합치기만 하고, fixture도 `fixtures/admin/`·`fixtures/office/`로 나눈다. 이유: W2의 두 화면 트랙이 같은 파일을 고치지 않게.
- 문서 파트 행: 세션 시작 시 `SessionService.start()`가 시나리오 parts 수만큼 `document_states`(빈 본문, revision 0)를 만든다. tasks는 분업 확정 때 api-candidate가 만든다. 이유: State 스냅샷과 문서 PUT이 행 존재를 전제로 단순해짐. 대안: PUT에서 upsert.
- `SCENARIOS_DIR`: 기본값(/scenarios)이 로컬에 없을 때만 저장소 `scenarios/`로 대체하고, 사용자가 지정한 경로가 없으면 설정 오류로 멈춘다. 이유: 잘못된 경로를 조용히 숨기지 않게.
- 소유권 예외 3건 수용: `scenarios/catalog.yaml`의 두 줄 인용(값 불변), `ruff.toml`의 Markdown 제외, `apps/web/README.md` 실행법.
- MVP 제외: 브로커가 발행을 확인한 뒤 큐가 유실된 경우의 복구(outbox는 `*_enqueued_at`이 비어 있는 세션만 재발행한다).

## 2026-10-20 api-admin 리뷰 반영 — **일부 대체됨(2026-10-21 토론형 전환)**: 업무 시뮬레이션 전용 항목(문서·보드·분업·카드 시각·관찰 레이블)은 대체, 일반 규칙은 유지
- 관찰 창(`current_element`): 가장 최근에 실행된 **요소 카드**의 요소다. 흐름 카드·결 메시지는 창을 닫지 않고, 마지막 요소 창은 제출 뒤 종료 실행이 끝날 때(completed 전)까지 열려 있다. 이유: 보고 단계의 지적도 창 안으로 봐야 한다. [product/scenario.md](product/scenario.md)·[architecture/agents.md](architecture/agents.md)의 예전 "흐름 카드도 창을 닫음" 문구는 이 결정이 우선한다.
- `Idempotency-Key` 헤더를 MVP 계약에서 뺀다. 멱등은 도메인 규칙(세션 전이, 내부 저장 키, 리뷰 본문 비교)으로만 보장하고 화면은 생성 POST를 자동 재시도하지 않는다. 이유: 초대 토큰 원문이 DB에 없어 키 기반 재응답을 복원할 수 없고 저장소를 더하는 비용이 크다. 대안: 멱등 키 테이블(제외).

## 2026-10-20 api-candidate 리뷰 반영 — **일부 대체됨(2026-10-21 토론형 전환)**: 업무 시뮬레이션 전용 항목(문서·보드·분업·카드 시각·관찰 레이블)은 대체, 일반 규칙은 유지
- 카드 실행은 세션별 due_at 직렬: 미완료(fired) 묶음이 done·failed·skipped가 되기 전에는 뒤 묶음을 디스패치하지 않는다. 재시작 복구도 같은 순서를 따른다. 이유: 상태를 가진 세션 그래프가 카드 순서를 뒤집어 처리하지 않게. 대안: retry를 events보다 먼저 호출(60초 미만 fired와 여러 pending 묶음 문제가 남음).
- 지원자 문서 PUT 권한: 분업 확정 전에는 모든 파트(리드가 초안을 잡을 수 있음), 확정 뒤에는 candidate·both만, colleague 단독 파트는 403. 이유: 동료 파트(정책 위반 포함)를 지원자가 직접 덮어쓰면 관찰 전제가 깨진다.
- **R5로 대체**(세션 Lock 없음, 문서 PUT 없음): 지원자 문서 PUT은 세션 Lock 안에서 상태를 다시 확인하고 저장한다. 내부 라우터는 Lock을 잡지 않는다. 이유: complete()와 직렬화해 종료 뒤 쓰기를 막되, 실행 중 runner의 내부 API 호출이 자기 Lock을 기다리는 교착을 피하려고. 대안: DB 행 잠금으로 complete와 공유(종료 경로 전체를 바꿔야 함).
- **R5로 대체**(디브리핑 기한 = `ended_at` + 7일, 실패해도 `ends_at`은 바꾸지 않음. [architecture/session-lifecycle.md](architecture/session-lifecycle.md) 세션 상태 머신): 디브리핑 기한은 세션 종료 시각(submitted_at, 진행 중 실패면 실패 시각) + 7일로 고정하고 debrief_token exp를 그 시각으로 발급, 지나면 410 expired. 진행 중 실패 시각은 `fail(session)`이 ends_at을 실패 시각으로 당겨 기록한다(별도 컬럼 없이). 리포트 단계 실패는 세션 종료가 submitted_at이므로 그 기준. 이유: GET마다 "지금부터 7일"을 발급하면 기한이 무기한 연장된다.
- 카드 3회 실패의 failed 기록과 SessionService.fail을 한 트랜잭션으로 하고, failed 필수 카드가 남은 in_progress 세션은 스케줄러 retry 단계가 fail로 수렴시킨다. 이유: 두 커밋 사이에 죽으면 세션이 진행 중으로 남아 만료 때 리포트까지 발행된다.
- 시작 공개 문서는 `SessionService.start()`가 시작 트랜잭션에서 released_at을 바로 기록한다. 이유: 첫 tick(최대 5초)까지 423이 되는 공백 제거, 지원자·내부·rag가 같은 시점부터 같은 상태를 봄.
- assistant_reuse의 revision 컬럼은 보류: 현재 내부 REST·워커 소비 계약에 revision이 없어 컬럼만 추가하는 효과가 없다. 순수 함수 반환값에만 revision을 둔다.
- `submitted_at` 이후 message.send는 상태와 무관하게 session_ending(접수 함수가 submitted_at을 status보다 먼저 검사).

- 가상 설정은 "새 프로젝트 팀"만. 루프랩·모아런 삭제.
- 유지: 오피스 시계, 디브리핑, 90일 보관, 금지 문구 검사(재생성 1회 → 안전 문구), 행동 유도 금지(화면 안내와 에이전트 문구는 기능 설명만), 인증(기업 관리자 / 초대 링크 지원자), 담당자 조정.
