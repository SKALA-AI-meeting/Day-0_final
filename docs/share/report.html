1.1 핵심 요약

60분 음성 토론 한 번으로 인성 5요소의 행동 근거를 남긴다.

지원자가 AI 동료 3명과 턴 기반 음성으로 키워드 · 문제 상황 · 해결책을 정하고 기획안을 내면, 평가 에이전트가 근거를 들어 수준을 제안하고 담당자가 최종 평가합니다.

표 1-1핵심 설계 결정

결정내용

재생이 끝나야 내 차례동료 발언은 검증된 최종 문장만 음성으로 바꿔 순서대로 재생하고, 실제 재생 종료를 확인한 뒤 지원자 차례를 연다

핵심 메시지

1.2 문제 정의와 서비스 구성

말로 묻는 검사 대신 회의 속 행동을 근거로 쓴다.

기업은 인성과 협업 태도를 중요하게 보지만 측정은 자기 보고와 짧은 면접에 기댑니다. Day Zero는 그 태도가 드러나는 회의 상황을 음성 토론으로 만들고 발언을 근거로 남깁니다.

표 1-2문제와 근거

문제근거
원하는 것과 재는 것이 다르다면접 유형은 질의응답이 94.1%, 실무 수행은 10.7%
자기 보고는 꾸밀 수 있다거짓말이 가장 잘 드러나는 전형으로 실무면접 65.5%, 인적성 검사 2.4%

지원자는 이유를 모른다취업준비생 51.5%가 최종 면접 불합격 통보조차 받지 못함

지원자가 받는 것

말이 아닌 행동으로 보여 줄 기회와 디브리핑. 어떤 장면이 설계되어 있었는지 설명하고 이의 제기 경로를 줍니다.

2.2 구성 요소와 배포

서비스는 8개이고, 업무 데이터는 api만 쓴다.

구성 요소마다 맡은 일과 하지 않는 일을 정해 경계를 지킵니다. 에이전트와 음성 턴 컨트롤러는 api 프로세스 안의 모듈이지만 계층은 라우터 → SessionService → AgentRunner → 그래프 → MCP 어댑터로 나눕니다.

3.1 에이전트 구성

참여자로 보이는 AI는 셋, 뒤에서 일하는 에이전트는 넷이다.

세션 중에는 api 안에서 의도 분류 · 토론 그래프 · 어시스턴트가 돌고, 세션이 끝나면 report-worker의 평가 에이전트가 돕니다.

표 3-1에이전트별 역할

에이전트하는 일도구
진행 매니저자극마다 화자 0~2명을 규칙으로 정하고, 규칙으로 정해지지 않은 지원자 발언에만 LLM을 씀결정적 노드가 debate-mcp 전부 · record_observation
페르소나 × 3성향 · 고정 입장 · 자리 기억(자기 발언 최대 3개)으로 1~2문장(약 120자) 발언get_transcript · get_draft · rag 2, 응답당 3회. DebateState는 컨텍스트로
의도 분류지원자 발언을 제안 · 동의 · 반대 · 질문 · 기타와 대상 안, 지명 대상으로 분류없음, 10초 넘으면 기타

3.2 음성 토론 한 턴

동료 발언이 끝까지 재생된 뒤에야 지원자 차례가 열린다.

음성 턴 컨트롤러는 토론 그래프 바깥에서 6개 상태를 관리합니다. 그래프 · 의도 분류 · guard · 합의 규칙은 텍스트 경로와 같고, 음성은 그 앞뒤에 녹음 · 받아 적기와 재생 확인을 붙입니다.

표 3-3음성 턴 규칙

규칙처리
차례 시작일반 · 손들기 · 강제 차례 모두 지원자가 [발언하기]를 눌러 시작합니다. 저절로 켜지는 녹음은 없고, 20초 안에 시작하지 않으면 동료 차례로 넘어갑니다
강제 차례그 단계에 지원자 발언이 없으면 단계가 절반 넘게 지난 뒤 마감 전에 단계당 한 번 옵니다(60분 세션은 마감 100초 전, 15분 키워드 단계는 75초 전)
받아 적기받아 적은 글은 지원자에게 보이지 않고 그대로 제출됩니다. 빈 인식 · 500자 초과는 다시 말하기를 안내하고, 500자 초과는 다시 녹음 1회와 따로 차례당 2회까지 받습니다
순서 보호녹음 · 전사 중 들어온 자극은 기다립니다. 게시 직전 generation이 바뀌었으면 남은 화자를 버리고, phase · generation이 바뀐 늦은 전사는 새 단계로 저장하지 않습니다
검사 · 실패guard · stance_check는 재생성 1회 뒤 고정 문구. TTS · 같은 파일 STT는 최대 2시도, 재생 오류는 발언권을 열지 않고 다시 재생을 묻습니다

3.3 단계 전환과 칸 확정

단계 시간과 칸 확정은 규칙이 정하고 LLM은 문장만 만든다.

칸 상태는 empty와 confirmed 두 개이고, 확정 경로에는 LLM이 없습니다. 칸마다 결과(합의 · 지원자 결정 · 시간 초과)와 채운 사람을 남깁니다.

표 3-4단계 중 사건과 처리

사건감지처리
지원자 확정[이걸로 정하기]확인 창 하나 뒤 칸 확정, 다음 단계로. 확정 순간 그 안의 지지자가 4명 중 3명 이상이면 "합의", 아니면 "지원자 결정". 녹음 · 전사 중이면 발언 제출 뒤에 가능
AI 합의 채우기진행 매니저 fill지원자 포함 3/4 지지면 fill_slot 한 번으로 api가 한 트랜잭션에서 재검사 · 칸 확정 · "그럼 X로 정리할게요." 저장 · generation +1. 409면 저장 없음

5. 평가 설계(BARS)

평가 에이전트는 근거가 있을 때만 수준을 내고, 최종 평가는 담당자가 한다.

세션이 끝나면 큐 작업으로 리포트 그래프가 돕니다. 요소마다 따로 호출해 다른 요소 결과를 보지 않게 하고, 초안 뒤에는 담당자 검토를 기다립니다. 근거는 제출된 발언 글이고 음색 · 억양 · 발음 · 말의 속도는 보지 않습니다.

7.1 음성 회의 화면

회의, 결정, 기획안 작성이 한 화면에서 이어진다.

현재 화면(발표자 보기)

실제 발언이 시작된 사람을 큰 칸으로, 나머지 셋을 작은 칸으로 보여 줍니다. 동료가 말하는 동안 재생 중인 문장이 실시간 자막으로 보이고, 재생이 끝나면 방금 한 말 한 문장만 남습니다. 발언 기록 목록은 없습니다. 지원자는 자기 발언을 글로 보거나 고치지 않습니다. 칸마다 지금 상태가 배지(발언 중 · 내 차례 · 준비 중 · 손 듦)로 붙고, 조작부 첫 줄은 "강한결님이 발언 중", "● 발언 중 0:12 / 1:00"처럼 지금 상태를 말하며, 진행을 막는 오류는 짧은 제목과 버튼 하나로 보입니다. 단계가 바뀌면 정한 키워드의 무드 색으로 전환 장면이 잠깐 지나갑니다.
