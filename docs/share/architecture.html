핵심 설계 결정

결정내용뷰
결정은 코드, 말투는 LLM입장 · 합의 · 카드 시각 · 시간 초과는 규칙이 정하고, LLM은 화자 보조와 발언 문장만②
턴 기반 음성 토론동료는 검증된 발언만 TTS로 차례대로 재생, 지원자는 [발언하기]로 직접 시작. 받아 적은 글은 비공개로 그대로 제출③‑1
세션별 메일박스자극 5종을 Task 하나가 직렬 처리. 새 지원자 메시지가 오면 남은 화자는 버림(generation). 녹음 · 전사 중 보류. 의도 분류 · 지지 반영은 항상 함③‑1
시간과 쓰기의 주인은 api시간 초과 채우기와 업무 데이터 쓰기는 api만(체크포인트 · 색인 예외). MCP와 워커는 /internal을 부름③‑2
근거 있는 판단, 확정은 사람평가 에이전트는 근거 없이 수준을 낼 수 없고, 담당자가 차원 단위로 조정③‑3
평가 정보 차단페르소나는 assessment-mcp에 닿지 않음(허용 목록 + 토큰)④

①설계 아키텍처 · 전체 구성도

Container · Client-Server. 브라우저는 api만 만나고, 에이전트는 api 안에서 MCP 세 개를 도구로 씁니다. 음성 발언권은 api 안의 Voice Turn Controller가 맡고 별도 MCP나 음성 서비스는 없습니다. 번호는 지원자 발언 한 번과 세션 종료 뒤 리포트까지의 처리 순서입니다.

표 1. 번호별 처리 흐름

번호구간처리 내용프로토콜

3api → 토론 그래프세션별 asyncio Task 하나가 메일박스의 자극 5종(message · phase_started · idle · turn_elapsed · card_due)을 순서대로 꺼내 AgentRunner.run(session_id, stimulus, run_id). 지원자가 녹음 · 전사 · 제출 중이면 실행을 보류프로세스 내부 호출

②에이전트 구성과 역할

세션 중에는 api 안에서 의도 분류 · 토론 그래프(진행 매니저 + 페르소나 3) · 어시스턴트가 돌고, 세션이 끝나면 report-worker의 평가 에이전트가 돕니다. 참여자로 보이는 것은 페르소나 3명뿐입니다.

진행 매니저

자극마다 누가 어떤 메시지에 답할지 정하고, 토론 상태 변경과 칸 채우기를 코드로 하는 보이지 않는 진행 담당

위치
토론 그래프 9노드 load → cards → turn → (화자마다 respond → guard → stance_check → wait_typing → apply) → fill. 체크포인터 없이 매 실행 load가 DB 상태를 다시 읽음
입력
메일박스의 자극 5종, DebateState(참여자당 현재 지지 하나 · consensus_option_id · 카드 진행 · 열린 지명), 최근 대화
판단
기존 합의(카드 전달 뒤면 fill, 미게시 카드가 있으면 fill_held) → 카드 화자 → 지명 응답(오래 기다린 자리부터, 넘치면 queued) → 전체 질문 → 침묵 초대 → turn_elapsed → 단계 첫 발언. 지원자 메시지에는 최소 1명: 카드 이끎 담당 → 턴 LLM → 기본 응답 자리(직전 AI 자리, 없으면 비판형 → 고집형)
출력
{speakers 0~2(turn_elapsed는 1), seat · reply_to · card_ids · invite, fill} → agent_runs.decision. 무엇을 말할지는 정하지 않음
모델
MODEL_TURN(message 자극에서 답할 화자가 규칙으로 정해지지 않을 때만)

페르소나 에이전트 × 3

지원자와 동등한 AI 동료. 지원자에게는 이름과 프로필 이미지, 목소리만 보임

위치
토론 그래프 respond, 진행 매니저가 고른 자리만 실행
입력
자기 성향 프롬프트, [상황](답할 메시지 · 지명 여부 · 카드 차례 · 내 지난 발언에 대한 반응 · 내 안을 두고 온 지원자 메시지), [내 입장], [카드 차례](목적, 카드 전에는 seed · bridge 차례), 자기 발언 3개 기억, 주입한 DebateState, 대화 30개
출력
{content, proposes?, stance?}, 음성으로 듣는 길이의 1~2문장 · 약 120자 요점 하나. 앞 발언을 받는 상투어로 시작하지 않고 바로 앞 화자와 같은 구조 · 근거를 되풀이하지 않음
보정
stance_check가 실제 지지 이동(move · withdraw, high)이면 1회 재생성 → 고정 문구. 자기 발언 3개 중 하나와 거의 같으면 1회 다시 씀. 정하는 방법을 묻는 질문이면 첫 화자 발언 앞에 정해진 안내문
볼 수 없음
평가 척도 · 관찰 · 카드 이름 · assessment 도구(허용 목록 ④)
모델
MODEL_PERSONA

실시간 의도 분류

지원자 메시지를 토론 상태로 바꾸는 작은 분류기(그래프 노드가 아님)

위치
api app/agent/intent. 메일박스가 message 자극을 꺼내면 그래프 전에 호출
입력
받아 적은 글, 저장된 메시지의 단계(messages.phase), 그 단계의 안 목록과 카탈로그 안 전체(아직 안 나온 안 포함), 직전 메시지 5개, 자리 이름
출력
{intent(propose · agree · oppose · withhold · question · other), target, new_option_label?, reservation, addressed_to, excluded, confidence}
쓰임
high이고 유보가 없는 agree · propose만 지지로 셈, withhold는 지지 철회. 지원자가 카탈로그 안을 먼저 말하면 최초 제안자는 지원자. 평가 수준에는 직접 쓰지 않음
실패
10초 타임아웃, 재시도 없음 → other · MODEL_INTENT, temperature 0. 동료 초안의 입장 판정(stance_check)도 같은 모델 역할을 별도 프롬프트로 씀

AI 어시스턴트

지원자만 쓰는 검색 · 요약 도우미(토론 참여자가 아니고 음성 큐에도 들어가지 않음)

방식
tool-calling 루프: 모델이 자료 도구를 부를지와 인자를 스스로 고름(허용 목록 ④, 요청당 최대 3회). LangGraph 그래프가 아니며 대화 이력은 세션별 프로세스 메모리
출력
답과 실제로 쓴 자료만 cited_material_ids, 쓴 자료가 없으면 출처 줄 없음. 자료 · 질문에 없는 숫자는 재생성 1회 뒤 남으면 그 문장 제거. 도구 호출 내역은 assistant_calls에 사실로 기록
경계
토론방 대화와 다른 참여자 정보는 보지 않음, 세션당 60회(넘으면 429), 요청당 LLM 7회 · 90초
모델
MODEL_ASSISTANT

평가 에이전트

세션 뒤 공개된 척도(BARS)로 차원별 수준을 근거와 함께 판단. 최종 평가는 담당자

위치
report-worker evaluate 노드, 세션 종료 후 큐 작업
입력
세션 대화 전체 · 칸 기록 · 기획안 제출본 · 카드 발생 기록 · 사실 지표 · facts.evaluator_facts(결정 시점 · 지원자 안 채택 · 핵심/보조 장면 · 선결정) · 메시지별 reply_to · Contributions와 그 요소의 척도 · 앵커. 음성 사용량 facts.voice_usage는 맥락만
출력
차원마다 {result(수준 1~5 | 기록 없음 사유), evidence[{ref, scene}], rationale, summary_line, confidence}. 요소 level · 요약은 워커 코드가 조립
호출
요소마다 따로, 다른 요소 결과는 넣지 않음(후광 방지). 실행 순서 · 검증은 ③-3
모델
MODEL_EVALUATOR, temperature 0.1, 도구 없음(워커가 입력 주입 · save_evaluation)

공통 규칙 (Harness)

모든 에이전트에 코드로 거는 안전장치

guard
생성 텍스트마다 무조건. 평가 관련 언급 · 연출 언급, 지원자 판정, 결론 대리 선언, 성향 이름, 미래 카드 암시 → 재생성 1회 → 자리별 안전 문구. 400자 상한. 토큰 스트리밍 없음
음성
TTS에는 guard · stance_check를 통과해 저장된 최종 본문만. 받아 적은 글은 phase · generation · epoch와 함께 검증
컨텍스트
페르소나에게 주지 않는 것: 평가 척도 · 관찰 · 카드 진행 · 다른 자리 성향 · 어시스턴트 대화 · 열리지 않은 자료
한도
실행당 화자 2명(turn_elapsed 1명), 응답당 도구 3회, 같은 자리 연속 3회 금지(카드 · 지명 응답 제외), 침묵 초대 단계당 1회
비용
cost_usd로 전체 관측(목표 $0.5). debate_cost_usd가 하드 상한 $2를 넘으면 페르소나는 고정 안전 문구만. 음성은 별도 사용량 원장으로 차단
멱등
agent_runs.status + DB 멱등 키. 200초 넘게 started인 run은 같은 run_id로 재실행

표 2. 세션 페르소나 3명 (모든 세션 고정)

자리이름 · 유형 · 목소리토론에서 하는 일맡는 장면

③흐름 · 음성 턴 · 단계 전환 · 평가 파이프라인

Sequence · Event-Driven. 지원자 발언은 받아 적은 글 한 건으로 세션 메일박스에 들어가 토론 그래프가 하나씩 처리하고, 동료 발언은 음성으로 차례대로 재생되며, 평가는 세션 종료 뒤 큐로 갑니다.

③-1 음성 토론 한 턴 · 지원자 발언 → AI 동료 발언

표 3-1. 음성 발언권 규칙 (Voice Turn Controller)

구분규칙
상태AI_GENERATING → AI_SPEAKING → USER_READY → USER_SPEAKING → TRANSCRIBING → PROCESSING. 원천은 DB voice_states(턴 · generation · epoch · 발언권)와 speech_jobs(합성 · 전사 · 재생 확인), 사용량은 speech_quotas
동료 차례진행 중인 실행이나 아직 재생하지 않은 TTS 항목이 있으면 동료 차례. 맨 앞 항목 합성이 끝나면 바로 재생하고, 브라우저가 항목마다 실제 ended를 보내야 다음 항목 · 마이크로 넘어감
내 차례실행과 재생이 모두 끝나면 USER_READY. 일반 · 손들기 · 강제 차례 모두 지원자가 [발언하기]로 시작하고 저절로 녹음되는 차례는 없음. 20초 유지 뒤 스케줄러가 동료 차례로 넘김(첫 초대는 idle, 이미 초대한 단계는 turn_elapsed로 동료 1명)
손들기동료 차례에 [손들기]를 누르면 재생 중인 발언은 끝까지 두고, 보호 발언(카드 발언 · 합의 / 시간 초과 공지)만 남긴 채 줄 선 동료 발언을 취소한 뒤 다음 차례를 지원자에게 줌
강제 차례토론 단계에 지원자 발언이 없고 마감까지 min(대기 30 + 발언 60 + 10초, 단계 길이 × 0.5) 이하가 남으면 단계당 한 번. "이번 단계에 OO님 의견도 들려주세요"를 보임
발언 길이서버가 /capture를 허가한 시각부터 최대 60초. 단계 마감 · 세션 종료 10초 전을 넘지 않고, 남은 시간이 짧으면 "이번 발언은 최대 N초"
받아 적기 · 제출Azure 빠른 받아 적기(구문 목록: 동료 이름 · 키워드 후보 · 현재 단계 안 라벨), 녹음 중 약 10초 단위 조각을 미리 받아 적음. 받아 적은 글은 지원자에게 보이지 않고 그대로 제출, 서버는 같은 글인지(앞뒤 공백만 허용) 확인해 다르면 voice_payload_mismatch
다시 말하기빈 인식 · 500자 초과는 제출하지 않음. 일반 다시 말하기는 차례당 1회, 500자 초과의 다시 말하기는 따로 차례당 2회
기획안 단계지원자 · 동료 모두 새 발언권 없음. 이전 단계의 대기 중 음성만 재생을 마치고, 지원자는 어시스턴트와 함께 혼자 작성
  • 끼어들기 대신 차례 · 동료 발언을 끊는 끼어들기(barge-in) · 동시 발언 · 부분 받아 적기 제출은 없습니다. 녹음 · 받아 적기 · 제출 중 들어온 자극은 DB에 queued로 남고 동료는 말하지 않습니다. 받아 적은 글이 저장되면 generation이 +1 되어, 실행 중인 그래프는 게시 직전 남은 화자를 버리고 새 메시지 자극이 이어서 처리합니다. 낡은 자극이라도 의도 분류와 지지 반영은 반드시 합니다.
  • 대화 리듬 · 한 실행의 동료 화자는 최대 2명이고 둘째 화자는 1~3초 간격, 차례가 넘어간 turn_elapsed는 1명만 말하고 바로 지원자 차례로 돌아옵니다. 동료 발언은 1~2문장 · 약 120자로 짧게 말합니다.
  • 화면 · 음성 회의는 발표자 보기입니다. 실제로 말을 시작한 사람을 큰 칸에, 나머지 세 명을 아래 줄에 둡니다. 동료 발언은 재생 중인 문장 자막과 재생 뒤 방금 한 말 한 문장만 보이고, 말풍선 · 입력창 · 발언 기록 목록은 없습니다. 지원자가 말한 글은 화면에 보이지 않고 저장되면 "전달했어요"만 보입니다.
  • 실패 · 복구 · 재생 · 받아 적기 실패는 명시적으로 다시 시도하며(같은 파일 최대 2시도) 무음 · 빈 받아 적기는 게시하지 않습니다. 업로드된 파일 · 받아 적기 · 재생 확인은 DB에서 복구하지만, 서버에 도착하기 전 녹음은 새로고침 때 복구할 수 없습니다. 페르소나 발언이 재시도 뒤에도 실패하면 그 발언만 생략(연속 3회면 세션 failed), turn LLM 실패는 기본 응답 자리, MCP upstream 실패는 1회 재시도합니다.
  • 공급자 · 사용량 · Azure F0 일반 Neural TTS(강한결 InJoon · 윤하람 SunHi · 서지안 BongJin)와 ko-KR STT입니다. 월 앱 한도 TTS 400,000자 · STT 14,400초에서 세션 시작 때 60분 세션은 12,000자 / 1,200초(15분 세션은 3,000자 / 300초)를 예약하고 호출 전에 차감합니다. 한도 초과 · 원장 장애 · F0 확인 실패면 호출을 막고 유료 음성으로 자동 전환하지 않습니다. 원음은 받아 적기 성공 뒤, 실패 원음 · TTS 자산은 최대 24시간 뒤 지웁니다.

③-3 평가 파이프라인 · report-worker

  • 사람 확인 · approval 노드의 interrupt에서 체크포인트를 먼저 저장한 뒤 draft 저장 → report_ready → ack 순서라, ack 뒤 승인이 와도 재개할 대상이 있습니다. 담당자가 차원 단위 조정 · 메모를 남겨 검토 완료하면 report.approve{session_id, eval_round}가 thread report:{session_id}:{eval_round}를 재개합니다. 평가를 다시 돌리면 새 회차 thread에서 collect부터 시작합니다. final은 draft content를 그대로 저장하고(해시 동일), 조정(rubric_adjustments)은 조회할 때 병합합니다.
  • 리포트 내용 · elements · dimensions(근거 원문 · 오피스 시각 · 앞뒤 맥락) · facts · contribution_check · seats · slots(칸 결과 outcome 포함) · debrief. 기록 없음은 화면에서 장면 없음(not_applicable · event_not_fired · preempted), 반응 없음(no_activity · auto_submitted_blank), 판단 보류(evaluate_failed, "판단 보류 · 근거 부족 — 원문 기록 확인 권장")로 묶습니다. 음색 · 억양 · 발음 · 말의 속도와 기획안의 질은 평가하지 않고, 결과를 한 줄로 줄인 합산 값은 만들지 않습니다.
  • 실패 · 노드 예외는 attempt+1 재발행(백오프 5 · 15 · 45초), 최초 포함 3회면 report.dlq → report_failed. 채용 건에 고정된 평가 프롬프트 복사본이 없으면 재시도 없이 바로 DLQ로 보냅니다.

④MCP 역할과 접근 경계

세 서버 모두 FastMCP · Streamable HTTP(도구는 async def)이고 api /internal을 불러 저장합니다(rag-mcp의 청크 검색 · 재색인만 직접). 상태 판단은 api가 하고 MCP는 전달만 합니다. 음성 경로는 새 MCP를 추가하지 않습니다. 오류는 {ok: false, error: {code, message, retryable}}입니다.
