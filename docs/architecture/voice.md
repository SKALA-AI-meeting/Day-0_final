# 음성 토론 구현

턴 기반 음성 토론의 현재 구현이다. 경로·필드·오류 코드는 [음성 계약](../contracts/voice.md), 결정과 이유는 [decisions.md](../decisions.md) "2026-10-22 턴 기반 음성 토론 전환 설계"(V1~V18)와 2026-10-25 음성 결정들이 정본이다.

지원자 1명과 AI 동료 3명이 발언권을 번갈아 갖는다. 동료는 검증을 마친 텍스트를 TTS로 순서대로 재생하고, 지원자는 마이크로 말한 뒤 받아 적은 글 한 건을 기존 WS `message.send`로 제출한다. 동시 발언, 동료 발언을 끊는 끼어들기(barge-in), 실시간 양방향 오디오, 부분 받아 적기 제출은 없다. 음색·억양·발음·말의 속도는 평가하지 않는다.

## 구성과 책임

| 구성 | 하는 일 | 하지 않는 일 |
|---|---|---|
| Voice Turn Controller(`services/api/app/voice/controller.py`) | DB `voice_states`·`speech_jobs`로 발언권 상태, 완료 장벽, 마감·손들기·강제 차례, turn_id·generation·epoch 검증 | 화자 선택, 입장·합의 변경, 평가 판단 |
| 음성 REST(`services/api/app/routers/voice.py`) | 상태 조회(polling), 녹음 시작·업로드·조각 전송, 재생 확인, 손들기, 다시 말하기, TTS 자산 제공 | 새 WS 이벤트 |
| Speech 어댑터(`services/api/app/voice/speech.py`) | 저장된 최종 본문 TTS, 완성 파일·조각 STT, F0 자원 확인. Azure·FakeSpeech 두 구현 | 문장 고쳐 쓰기, MCP 접근 |
| 사용량 원장(`services/api/app/voice/quota.py`) | 월·세션 사용량 예약과 차감, 호출 속도 제한 | 유료 전환 |
| 정책(`services/api/app/voice/policy.py`) | 채용 건 생성 때 `positions.scenario.voice_policy`에 고정할 값 | 진행 중 env로 정책 보충 |
| 메일박스·토론 그래프 | 기존 의도 분류·화자 0~2명·guard·stance_check·apply·fill | 재생을 기다리며 트랜잭션·락 유지 |
| 브라우저(`apps/web/components/debate/voice/`의 `voice-room.tsx`·`recorder.ts`·`streamer.ts` 등, `voice-ui.tsx`·`voice.ts`) | 상태 반영, 단일 오디오 큐, 녹음·업로드·조각 전송, 실제 재생 결과 보고 | 서버 턴을 혼자 완료 처리 |

동료 발언은 1~2문장·약 120자 안쪽의 요점 하나로 말하고(프롬프트 규칙, guard 상한 400자는 그대로), 앞 발언을 받는 상투어로 시작하거나 바로 앞 화자와 같은 구조·근거로 말하지 않는다([agents/persona.md](../agents/persona.md)). TTS는 `guard`·`stance_check`를 통과해 `apply`가 저장한 최종 게시 본문만 받는다. 합의 채움·시간 초과의 고정 공지도 음성 항목에 포함한다. 토론 그래프 체크포인터·새 MCP·음성 전용 서비스는 없다. 재생 대기 동안 DB 락이나 메일박스를 붙들지 않는다.

## 발언권 상태와 완료 장벽

상태는 AI_GENERATING → AI_SPEAKING → USER_READY → USER_SPEAKING → TRANSCRIBING → PROCESSING이다. 막힘·실패 이유는 `blocked_reason`(값과 조건은 [음성 계약](../contracts/voice.md))으로 표시한다.

- **동료 차례**: 진행 중인 에이전트 실행(`agent_runs` queued·started)이나 아직 재생하지 않은 TTS 항목이 있으면 동료 차례다. 맨 앞 항목의 합성이 끝나면 뒤 항목·실행이 남아 있어도 바로 재생한다(AI_SPEAKING). 남은 항목이나 실행이 있는 동안은 내 차례가 되지 않는다.
- **재생 확인**: 브라우저는 첫 미완료 항목의 `start`와 실제 `ended`를 `/playback`으로 보내야 다음 항목으로 넘어간다. `play()` 성공이나 생성 완료는 청취 완료가 아니다. 들은 항목은 `heard`이고, 단계가 바뀌면 이전 단계의 일반 발언은 재생하지 않는다(합의·시간 초과 공지는 재생).
- **내 차례(USER_READY)**: 실행과 재생이 모두 끝나면 열린다. AI 발언이 0개면 바로 열린다. 일반·손들기·강제 차례 모두 지원자가 [발언하기]를 눌러 시작하고, 녹음이 저절로 시작되는 차례는 없다. 채용 건의 `turn_hold_seconds`(기본 20초) 동안 차례를 지키고, 지나면 스케줄러가 동료 차례로 넘긴다(첫 초대는 `idle`, 이미 초대한 단계는 `turn_elapsed`). `turn_elapsed`로 넘어간 동료 차례는 한 명만 말해 바로 지원자 차례로 돌아온다(카드 화자·지명 응답도 이 상한에 들고, 넘친 것은 다음 실행으로 넘어간다). 다른 자극은 최대 2명이다. 실제로 넘기기 전까지는 [발언하기]가 된다. 실패 뒤 다시 녹음으로 돌아오면 유지 시간이 새로 시작된다.
- **손들기**: 동료 차례(AI_GENERATING·AI_SPEAKING)에 손을 들면 지금 재생 중인 발언은 끝까지 두고, 보호 발언(카드 발언·합의/시간 초과 공지)만 남긴 채 줄 선 동료 발언을 취소한 뒤 내 차례를 준다. 실행 중인 에이전트가 있어도 준다.
- **강제 차례**: 키워드·문제 상황·해결책 단계에서 그 단계 지원자 발언이 없고 마감까지 `min(forced_wait_seconds + user_turn_seconds + 10, 단계 길이 × 0.5)`초 이하가 남으면 단계당 한 번 온다(기본 정책에서 60분 세션은 모든 단계 마감 100초 전, 15분 세션 키워드 단계는 75초 전, 문제 상황·해결책은 100초 전). 동료 차례면 손들기와 같이, 일반 내 차례면 그 자리에서 강제 차례가 된다. 버튼 위에 "이번 단계에 OO님 의견도 들려주세요"를 보인다.
- **지난 발언 정리**: 지원자 메시지보다 먼저 만들어졌는데 재생이 시작되지 않은 동료 발언은 보호 발언이 아니면 재생하지 않는다(`superseded`).
- 기획안 단계에는 지원자·동료 모두 새 발언권이 없다(`blocked_reason: proposal_phase`, 녹음 요청은 409 `voice_turn_expired`). 질문 차례가 다시 열리지 않으며, 단계 전환 전 대기 중이던 동료 음성만 재생을 마친다. AI 어시스턴트는 음성 큐에 들어가지 않는 별도 기능이다.
- 녹음·받아 적기·제출 중(USER_SPEAKING~PROCESSING) 새 자극은 DB에 queued로 남고 동료가 말하지 않는다. 침묵 초대는 단계당 한 번 그대로다.

## 화면

음성 회의 화면은 발표자 보기다. 채팅 입력창·말풍선·입력 중 표시·발언 기록 목록은 없다.

- 실제 발언이 시작된 사람을 큰 칸에 보이고 나머지 세 명은 아래 줄에 둔다(`profile-stage.tsx`). 말하는 사람 강조는 세 동료가 같은 모양이고, 이름과 아바타로 구분해 색만으로 알리지 않는다.
- 동료가 재생 중인 문장은 큰 칸에 실시간 자막으로 보이고(재생 위치까지의 문장만), 재생이 끝나면 방금 한 말 한 문장만 남는다. 미재생 발언은 미리 보이지 않는다.
- 지원자 자신이 말한 글은 화면에 보이지 않고 고칠 수도 없다. 저장되면 "전달했어요"를 3초 보인다.
- 조작부 첫 줄은 지금 상태를 말한다: 첫 상태를 받기 전 "회의 상태를 불러오는 중…", 다시 잇는 중이면 끊김 표시, 동료 차례에는 "강한결님이 말하는 중"처럼 말하는(준비하는) 동료 이름, 녹음 중에는 "● 녹음 중 0:12 / 1:00"과 음량 파형·큰 [발언 완료](내 프로필이 음량만큼 빛남). 내 차례 유지 시간은 큰 숫자와 줄어드는 막대로 보이고, 글 쓰는 곳이나 버튼에 포커스가 없으면 Space로 [발언하기]를 누를 수 있다.
- 진행을 막는 오류는 경고 아이콘·짧은 제목·할 일 문장과 그 일을 하는 버튼 하나(다시 보내기·다시 재생·다시 받아 적기·다시 녹음·다시 연결)로 보이고, 막지 않는 안내는 회색 한 줄로 6초 뒤 사라진다. 다시 시도 횟수를 다 쓰면 버튼 없이 "다음 차례에 말해 주세요"를 보인다. 녹음 중 연결이 끊겼다 이어지면 "끊긴 동안의 발언은 저장되지 않았어요. 다시 말해 주세요"를 보인다.
- 결정 사항(기획안 단계는 기획안)은 오른쪽 위, 자료·AI 어시스턴트 탭은 오른쪽 아래, 메모장과 단계 안내는 왼쪽이다. 메모는 그 브라우저(localStorage)에만 세션별로 저장하고 서버로 보내지 않으며 평가에 쓰지 않는다.
- 브라우저는 `/voice`를 평소 750ms, AI_GENERATING·TRANSCRIBING·PROCESSING 동안 250ms 간격으로 조회한다.

## 지원자 발언과 시간

- 시작 전 마이크 권한을 확인한다. 권한 요청이 8초 안에 끝나지 않으면 안내와 재시도 버튼을 보이고, 늦게 열린 스트림은 닫는다.
- 발언 한도는 채용 건의 `user_turn_seconds`(기본 60초, `VOICE_USER_TURN_SECONDS` 1~60)이고 서버가 `/capture`를 허가한 시각부터 잰다. AI 생성·재생 시간은 한도에 넣지 않는다. 녹음 마감은 단계 마감·세션 종료 10초 전을 넘지 않고, 그 10초 안에서는 녹음을 시작할 수 없다. 남은 시간이 한도보다 짧으면 "이번 발언은 최대 N초"를 알린다(`speech_limit_seconds`). 단계 마감·세션 종료는 늘리지 않는다.
- [발언 완료]와 타이머는 같은 1회 종료 함수를 쓴다. 마지막 녹음 조각 뒤 브라우저가 PCM16 mono 16kHz WAV 한 파일로 만들어 `/audio`로 올린다(같은 파일 해시면 멱등).
- 받아 적은 글은 지원자에게 보이지 않고 `client_msg_id = utterance_id`로 바로 `message.send`한다. 서버는 같은 세션·턴·epoch·generation의 ready STT 작업과 제출 글이 같은지(앞뒤 공백만 허용) 확인하고, 다르면 `voice_payload_mismatch`로 거부한다. 제출 글에 기존 마스킹을 적용하며, 이 글이 곧 받아 적은 글이라 원문을 따로 두지 않는다. 토론 그래프·평가·관리자 전체 기록은 이 글을 쓴다.
- 지원자 발언은 앞뒤 공백을 뺀 1~500자다(서버 `CANDIDATE_MESSAGE_MAX_CHARS`와 화면 `state.ts`가 같은 값). 빈 인식과 500자 초과는 제출하지 않고 [다시 말하기]를 안내한다. 일반 다시 말하기는 차례당 1회, 500자 초과로 다시 말하기는 따로 차례당 2회까지다. 녹음 시작은 차례당 2회가 상한이다.
- phase·generation이 바뀌면 미디어를 멈추고 늦은 받아 적기를 새 단계에 저장하지 않는다. 녹음·받아 적기·제출이 끝나기 전에는 결정 사항 확정을 할 수 없다.

## 받아 적기(STT)

- 기본 경로는 Azure 빠른 받아 적기(fast transcription REST 한 번)다. 구문 목록(`phraseList`, `controller.py` `stt_phrases`)으로 동료 이름, 키워드 후보 라벨, 현재 단계의 카탈로그 안 라벨(문제 상황·해결책은 확정 키워드의 것)을 함께 보낸다. 값은 모두 채용 건 복사본에서 읽고 500개 안에서 자른다. 거절되면 같은 파일을 SDK continuous recognition으로 끝까지 읽어 최종 구간을 합친다(둘 다 F0 안의 경로).
- 녹음 중 브라우저가 약 0.5초마다 PCM 조각을 `/stream`으로 보내면, 서버가 `VOICE_SEGMENT_SECONDS`(기본 10초)가 쌓일 때마다 직전 `VOICE_SEGMENT_SEARCH_SECONDS`(4초) 안에서 가장 조용한 `VOICE_SEGMENT_PAUSE_MS`(300ms) 구간을 찾아 잘라 미리 받아 적는다. `/audio` 뒤에는 남은 꼬리만 받아 적어 잇는다. 순번이 빠지거나 받은 길이가 완성 파일과 1초 넘게 다르면 완성 파일 전체로 받아 적는다. 조각 전송이 없어도 `/audio`만으로 동작한다. 제출되는 글은 발언 하나에 하나다.
- 지원자 입력은 단일 채널이고 AI TTS를 다시 받아 적지 않는다.

## Azure와 사용량

- TtsService·SttService는 토론 에이전트와 독립 인터페이스다. 기본 어댑터는 Azure F0 일반 Neural TTS와 표준 ko-KR STT이고, 자리별 voice는 p1 `ko-KR-InJoonNeural`·p2 `ko-KR-SunHiNeural`·p3 `ko-KR-BongJinNeural`로 채용 건에 고정한다. 말투·입장은 텍스트 프롬프트와 결정적 규칙이 정하고 감정 스타일로 성향을 과장하지 않는다.
- F0 자원 조회와 listKeys로 자원·지역·키 소속을 확인하고(성공은 60초 동안 재사용), 확인할 수 없으면 503 `voice_unavailable`로 막는다. 다른 공급자 자동 대체·S0 전환은 없고, 관리 자격증명에는 요금제 변경 권한을 주지 않는다.
- 월 운영 한도는 전용 자원 기준 TTS 400,000자·STT 14,400초(F0 무료량 50만 자·5시간보다 낮음)다. 세션 시작 때 60분 세션은 12,000자/1,200초, 15분 세션은 3,000자/300초를 예약하고, 실제 호출 전에 차감하며, 종료 세션의 미사용량은 반환한다. 타임아웃·재시작으로 과금 여부가 불확실해도 차감을 되돌리지 않는다. 한도 부족은 409 `voice_quota_exhausted`, 세션당 TTS 100회·STT 40회와 공용 TTS 15회/60초를 넘으면 차단이다. Azure 음성 세션은 한 번에 하나만 허용한다(409 `voice_capacity`). FakeSpeech는 여러 격리 세션을 허용한다.
- `VOICE_QUOTA_PERIOD`는 원장 기간 ID다. `auto`는 UTC 연-월(`YYYY-MM`)마다 새 원장, 다른 값은 그대로 ID, 빈 값은 음성을 막는다. 같은 키를 외부 도구와 나눠 쓰면 원장 밖 사용이 생기므로 전용 자원을 쓴다.
- `SESSION_COST_HARD_USD`는 토론 LLM만 대상이다. 음성은 작업마다 단위·수량·시도·순비용 0·청구 상태를 따로 남기고, 불확실한 호출의 순비용은 null이다. SessionRecord `facts.voice_usage`에서 사용량과 불확실 상태를 본다. 유료 음성과 통합 유료 비용 상한은 없다.

## 오류·복구·평가

- 재생은 실패한 항목부터 캐시 자산으로 다시 한다. 자산이 없는 TTS와 같은 파일 STT는 최대 2시도이고 자동 무한 재시도는 없다. 공급자 작업은 호출 전 processing을 커밋하고, TTS processing이 120초 넘게 남으면 오류(`voice_timeout_unknown`)로 바꿔 명시적 재시도를 요구한다. 생성·받아 적기 실패는 작업 error `voice_speech_failed`, 재생 실패는 `voice_playback_failed`로 남는다. 발언권은 녹음 마감 + 100초를 넘기지 않는다.
- 빈 받아 적기는 메시지를 만들지 않는다. 마이크·장치 오류는 기능 안내이며 행동 근거가 아니다.
- WS 재연결은 새 epoch를 발급하고 이전 epoch 명령과 이전 탭 제출을 거부한다. 녹음 중 재연결되면 그 발언은 버리고 다시 말하게 한다(`voice_interrupted`). 업로드된 파일·받아 적기·재생 확인은 DB로 복구하고, ack가 사라지면 같은 ID로 다시 제출한다. 서버에 도착하기 전 새로고침·연결 끊김으로 잃은 녹음은 복구하지 못한다. 브라우저가 들은 뒤 확인이 유실되면 그 항목을 다시 들을 수 있다.
- 카드 게시 기록은 그대로 두고, 음성 세션의 `observations.delivered`는 담당 자리의 TTS `ended` 확인이 모두 있어야 true다. 발언 없는 카드는 기존 관찰을 유지한다. 음성 장애·미청취 메시지·불확실 비용은 facts로 전달하며 행동 근거가 아니다. 척도·앵커·평가 모델은 텍스트와 같다.
- 원음은 받아 적기 성공 때 지우고, 실패 원음·TTS 자산은 최대 24시간 뒤 지운다. 세션이 끝나면 다음 스케줄러 틱에 오디오 bytes를 비운다. 상태·전사·사용량 기록은 세션 보관 기간에 묶여 세션 삭제 때 함께 지워진다([data-model.md](data-model.md)). 자산은 세션 JWT·소속 확인 뒤 `no-store`로 준다.

## 실행·검증

- 모드는 실행 프로필이 정한다([guides/configuration.md](../guides/configuration.md)): `dev-real`·`deploy`는 Azure, `dev-fake`·`test-voice`·`eval-voice`는 FakeSpeech, `test-text`·`eval-text`는 음성 끔(텍스트 WS 경로, `ENABLE_TEST_API=1` 필요). 채용 건의 `voice_policy.provider`가 실행 공급자와 다르면 시작을 거부한다.
- Azure 설정은 `infra/.env`에만 둔다. 새 DB는 `infra/db/schema.sql`을 적용하고, 기존 로컬 DB는 [DB 가이드](../guides/database.md)를 따른다.
- FakeSpeech TTS는 짧은 무음 WAV이고 한국어 음질 검증이 아니다. 내부 `/internal/test/voice-transcript`로 받아 적을 글만 지정하고, 음성 프로필의 화면 테스트는 실제 브라우저의 녹음·업로드·재생 이벤트를 거친다. Fake 통과를 실제 공급자 검증으로 보지 않는다.
- 알려진 한계: 끼어들기(barge-in)는 없다. 음성 경로의 지연(말 끝 → 다음 동료 목소리)과 실제 Azure 한국어 품질은 측정 기록이 없다.
